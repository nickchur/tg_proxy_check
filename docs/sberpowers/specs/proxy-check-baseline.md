# Baseline-спека: мониторинг семейных MTProto-прокси (tg_proxy_check)

- Дата: 2026-10-07
- Статус: подтверждена
- Источник: обсуждение 2026-10-07 (вынос проверки прокси из tg_news_digest; решения: обе проверки в одном репо, туннель — отдельный репо tg_tunnel, внешняя проверка — отдельный Cloudflare Worker, уведомления через /notify дайджеста, скрипты хостов — sh)

## Назначение

Владелец узнаёт в Telegram, когда семейный прокси перестал работать и когда ожил — независимо от того,
работает ли дайджест новостей. Обе проверки (внешняя проверка портов и проверка службы и туннеля на стенде) лежат в одном репозитории
и выкладываются одной командой. Сам туннель — отдельный репозиторий tg_tunnel.

## Требования

- **REQ-pxc-01** — Каждые 5 минут отдельный Cloudflare Worker `tg-proxy-check` пытается открыть TCP-соединение
  с каждым прокси из переменной `PROXIES` («host:port,host:port»); соединение не открылось за 10 с — неудача.
- **REQ-pxc-02** — После 2 неудач подряд по прокси владелец получает одно сообщение «⚠️ Прокси host:port не
  отвечает N мин»; дальнейшие неудачи повторных сообщений не дают.
- **REQ-pxc-03** — Первая удача после объявленного падения даёт одно сообщение «✅ Прокси host:port снова отвечает».
- **REQ-pxc-04** — Состояние каждого прокси ({fails, down}) переживает перезапуски Worker'а и пишется только при
  изменении.
- **REQ-pxc-05** — Сообщения уходят через `POST /notify?key=<ADMIN_KEY>` Worker'а tg-digest по service binding;
  у Worker'а tg-proxy-check нет токена бота.
- **REQ-pxc-06** — Пустой `PROXIES` — Worker ничего не проверяет и ничего не шлёт, без ошибок.
- **REQ-pxc-07** — Скрипт проверки стенда (служба mtg активна; SOCKS 127.0.0.1:1080 доводит до api.telegram.org)
  лежит в репозитории и ведёт себя как сейчас на стенде (2 неудачи → ⚠️, ожил → ✅).
- **REQ-pxc-08** — Одна команда выкладки ставит Worker (код, секреты, cron, binding) и раскладывает скрипт на
  стенд с его cron; адреса хостов и прокси берутся из секрета `tg-proxy-check` в Bitwarden, в репозитории
  их нет.
- **REQ-pxc-09** — Логика разбора `PROXIES` и переходов состояния покрыта тестом, который запускается в node без
  Cloudflare.

## Ограничения и контракты

- Бесплатный тариф Workers: вызов укладывается в 10 мс CPU (ожидание сокета не считается); не больше 50
  подзапросов. Cron — `*/5 * * * *`.
- Хранилище — собственный бакет R2 `tg-proxy-check`, ключ `proxy:<host>`, значение `{"fails":n,"down":bool}`.
- Секреты Worker'а: `ADMIN_KEY` (тот же, что у tg-digest), `PROXIES` (plain). Binding `DIGEST` → сервис tg-digest.
- Скрипты хостов — POSIX sh, только то, что уже стоит на хостах (curl, systemctl). Пути и cron на
  хостах прежние, чтобы выкладка была заменой, а не переездом.
- Публичный репозиторий github.com/nickchur/tg_proxy_check: ни IP, ни ключей, ни имени бота (`@your_bot`).

## Non-goals

- Проверка через MTProto-рукопожатие или реальный трафик Telegram из Worker'а — только TCP-порт.
- Своя Telegram-доставка (токен бота) — уведомления только через /notify дайджеста.
- Автопочинка (перезапуск mtg, туннеля) по сигналу Worker'а.
- Обратный туннель с GCP (tg-tunnel) — отдельный репозиторий tg_tunnel.
- Управление прокси (выпуск секретов mtg, раздача ссылок) — остаётся ручным.

## Критерии приёмки

| REQ-ID | Сценарий проверки |
|---|---|
| REQ-pxc-01 | В PROXIES добавлен заведомо закрытый порт → через 10 мин пришло ⚠️ по нему, по живым прокси сообщений нет |
| REQ-pxc-02 | Закрытый порт держится 30 мин → ровно одно ⚠️ |
| REQ-pxc-03 | Порт убран из PROXIES или открыт → после открытия ровно одно ✅ |
| REQ-pxc-04 | В R2 `tg-proxy-check` есть `proxy:<host>` по каждому прокси; время изменения объекта живого прокси не обновляется каждые 5 мин |
| REQ-pxc-05 | Сообщение приходит в личку от бота дайджеста; в настройках Worker'а tg-proxy-check нет BOT_TOKEN |
| REQ-pxc-06 | PROXIES пуст → за 15 мин ни одного сообщения, в аналитике Worker'а нет ошибок |
| REQ-pxc-07 | `systemctl stop mtg` на стенде → через ≤10 мин ⚠️ «служба mtg не работает»; старт → ✅. |
| REQ-pxc-08 | Чистый клон + `./deploy.sh` → Worker, cron, binding на месте; на стенде файл скрипта совпадает с репо; `grep` по репо не находит IP |
| REQ-pxc-09 | `node test/test_check.mjs` проходит; ломка порога в 2 неудачи роняет тест |
| все | За сутки в аналитике Worker'а нет exceededResources |
