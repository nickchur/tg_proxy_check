# Delta-спека: свой бот и /notify в tg-proxy-check

- Дата: 2026-10-07
- Статус: подтверждена
- Baseline: docs/sberpowers/specs/proxy-check-baseline.md
- Источник: обсуждение 2026-10-07 — мониторинг не должен зависеть от дайджеста, о котором ему может понадобиться сообщить

## Мотивация

Сейчас ⚠️/✅ идут через `/notify` Worker'а tg-digest: сломался или переразвёрнут дайджест — тревоги о прокси
молча пропадают. У мониторинга будет свой бот и свой `/notify`; им же пользуются скрипт стенда и `tg-me`.
У дайджеста после этого Worker'а на Cloudflare не остаётся (его парная спека — в tg_news_digest).

## ADDED — новое поведение

- **REQ-pxc-12** — `POST https://tg-proxy-check.<subdomain>.workers.dev/notify?key=<ADMIN_KEY>`, тело — текст
  (HTML Telegram можно), отправляет текст владельцу (`OWNER_ID`) в личку от своего бота и отвечает `200 ok`.
  Неверный или пустой ключ — `403`, пустое тело — `400`, Telegram не принял — `502` с его описанием.
  Другие пути и методы — `404`.
- **REQ-pxc-13** — Текст длиннее лимита Telegram уходит несколькими сообщениями по ≤ 4000 символов, без потерь.

## MODIFIED — изменённое поведение

- **REQ-pxc-05** — было: сообщения уходят через `/notify` Worker'а tg-digest по service binding, токена бота у
  tg-proxy-check нет → станет: Worker шлёт ⚠️/✅ сам через Telegram Bot API своим ботом (`BOT_TOKEN`, получатель
  `OWNER_ID`); binding'а на tg-digest нет; неуспех Telegram — ошибка отправки (REQ-pxc-10 действует как прежде).
- **REQ-pxc-07** — было: скрипт стенда шлёт через /notify дайджеста → станет: через /notify tg-proxy-check
  (меняется только URL в `/etc/mtg-check.env`, ключ тот же).
- **REQ-pxc-08** — дополнительно: выкладка включает поддомен workers.dev для tg-proxy-check (нужен `/notify`
  снаружи) и ставит секреты `BOT_TOKEN`, `OWNER_ID`; токен бота, как и токен Cloudflare, не попадает в аргументы
  процессов.

## REMOVED — удаляемое поведение

- Service binding `NOTIFY` → tg-digest. Потребитель — сам Worker: переходит на прямую отправку (REQ-pxc-05).

## Ограничения и контракты

- Контракт `/notify` совпадает с прежним у tg-digest (тот же `ADMIN_KEY`, то же тело) — переключение
  потребителей = смена хоста в URL.
- Потребители `/notify`: Worker (внутренний вызов, без HTTP к себе), `mtg-check` на стенде, `tg-me` на рабочей
  машине. `tg-me` передаёт ключ не в аргументах curl.
- Секрет `tg-proxy-check` в Bitwarden: добавляются `BOT_TOKEN`, `OWNER_ID`.
- Бот новый (заводит владелец у @BotFather) и должен получить от владельца `/start` — иначе Telegram не даст
  написать первым.
- Бесплатный Workers: 10 мс CPU, 50 подзапросов — отправка в Telegram укладывается.

## Non-goals

- Команды боту мониторинга (статус, пауза) — бот только пишет.
- Публикация в группу или канал — только личка владельца.
- Повторы отправки внутри одного вызова — повтор делает следующий cron (REQ-pxc-10).

## Критерии приёмки

| REQ-ID | Сценарий проверки |
|---|---|
| REQ-pxc-12 | `curl --data-binary 'тест' …/notify?key=<верный>` → 200 и сообщение от нового бота; неверный ключ → 403; пустое тело → 400; GET /notify → 404. Тест в node с подменой `fetch` Telegram покрывает все коды |
| REQ-pxc-13 | Тест: текст 9000 символов → три вызова sendMessage, склейка = исходный текст |
| REQ-pxc-05 | Тест: переход в down → sendMessage к `api.telegram.org/bot<BOT_TOKEN>/` с `chat_id=OWNER_ID`; Telegram отвечает ошибкой → состояние не записано. Живьём: закрытый порт → ⚠️ от нового бота; в настройках Worker'а нет binding'а `NOTIFY` |
| REQ-pxc-07 | `systemctl stop mtg` → ⚠️ от нового бота; `/etc/mtg-check.env` указывает на tg-proxy-check |
| REQ-pxc-08 | `./deploy.sh` → поддомен включён, `BOT_TOKEN`/`OWNER_ID` в настройках Worker'а; `ps` во время выкладки без токенов |
| — | `tg-me "тест"` приходит от нового бота |
